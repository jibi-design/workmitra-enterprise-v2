# 1. WORKMITRA / JOB MITRA — BACKEND AND LOGIN MASTER DOCUMENT

## 1.1. Document Status

Status: Enterprise upgraded and final-lock approved  
Scope: Backend, login, account, API, database, permissions, security, privacy, migration and release readiness  
Applies to: Job Mitra public app and WorkMitra internal continuity  
Does not replace: Core Master Truth or domain architecture documents

## 1.2. Inherits From

This document inherits:

- `01_CORE_MASTER_TRUTH.md`
- `12_CROSS_DOMAIN_SYSTEM_RULES.md`
- `13_UI_DESIGN_SYSTEM_RULES.md`
- Mitra Labs Universal Working Agreement v3.1.2

If this document conflicts with Core Master Truth, Core Master Truth wins.

## 1.3. Purpose

This document defines the backend and login master architecture for Job Mitra.

It exists to make the app ready for real production backend work without mixing backend rules into Shift Jobs, Career Jobs, Work Vault or other domain documents.

Backend/Login is a separate foundation layer.

It must support all product domains safely through shared identity, permission, storage, API, audit and sync rules.

## 1.4. Core Principle

Backend and login must make Job Mitra:

- secure
- role-safe
- scalable
- privacy-safe
- Play Store compliant
- backend-ready
- domain-neutral
- audit-friendly
- future-expandable

Backend/Login must not change product truth.

It only enforces product truth.

## 1.5. What Backend/Login Is

Backend/Login is:

- account creation and sign-in system
- user identity foundation
- Employer / Employee role context foundation
- secure session system
- permission enforcement layer
- API gateway layer
- database persistence layer
- audit / timeline support layer
- account deletion / privacy control layer
- local-to-backend migration foundation

## 1.6. What Backend/Login Is Not

Backend/Login is not:

- Shift Jobs business logic document
- Career Jobs business logic document
- Work Vault feature document
- HR Section
- Admin product UI
- payment system
- payroll system
- legal employment verification system
- messaging/social chat system

## 1.7. Hard Separation Rule

Backend/Login must remain separate from product domain logic.

Domain documents define what the product does.

Backend/Login defines how accounts, data, permissions and server execution are safely managed.

Example:

- Shift Jobs decides what `standby` means.
- Backend stores, protects and permission-checks standby records.

Backend must not silently convert one domain state into another.

# 3. LOGIN AND AUTHENTICATION ARCHITECTURE

## 3.1. Authentication Principle

Authentication must confirm who the user is.

Authorization must confirm what the user can do.

These two must never be confused.

## 3.2. Approved Login Methods

Recommended launch/backend login methods:

1. Email + password
2. Phone number + OTP, only if real provider and policy-safe
3. Google Sign-In, optional
4. Passkeys, future advanced option
5. Magic link, optional future option

## 3.3. Email + Password Rules

Required:

- password hashing using strong modern algorithm
- password reset flow
- email verification flow where needed
- rate limiting
- brute-force protection
- suspicious login monitoring
- session revocation

Blocked:

- plain text password storage
- weak password rules without throttling
- password in logs
- password in URL
- password sent back through API response

## 3.4. Phone OTP Rules

Phone OTP is allowed only when real SMS/OTP infrastructure exists.

Phase-0/demo must not claim real OTP.

Production OTP rules:

- short expiry time
- retry limits
- resend cooldown
- abuse detection
- phone number verification status
- OTP never logged
- OTP never exposed to client after generation

Blocked:

- fake OTP shown as real verification
- static OTP in production
- unlimited OTP attempts
- OTP used as hidden payment or identity proof claim

## 3.5. Google Sign-In Rule

Google Sign-In may be used as a convenience login method.

Rules:

- still create internal `USER_ACCOUNT`
- still enforce Employer / Employee role context
- do not rely on Google account as job identity authority
- allow account deletion path
- handle email changes carefully

## 3.6. Password Reset Rule

Password reset must include:

- verified email/phone path
- short-lived reset token
- one-time use
- rate limiting
- success/failure safe wording
- active session review after reset

Do not reveal whether an account exists through unsafe wording.

Safe wording:

```txt
If an account exists, we will send recovery instructions.
```

## 3.7. Session Model

Recommended production model:

- short-lived access token
- refresh token with rotation
- server-side token revocation list or session table
- secure transport only
- device/session visibility for user where possible

Rules:

- logout must invalidate session where supported
- password reset should revoke risky sessions
- deleted account must invalidate all sessions
- tokens must not be stored in unsafe plain localStorage for web production

## 3.8. MFA / Two-Step Future Rule

Future MFA may include:

- authenticator app
- email challenge
- phone OTP
- passkey
- backup codes

Rules:

- MFA must be optional first unless risk requires it
- recovery must be safe
- do not lock users out without recovery path
- hidden Admin accounts should require stronger MFA in production

# 4. AUTHORIZATION AND PERMISSION SYSTEM

## 4.1. Authorization Principle

Every important backend action must check:

- authenticated user
- active role context
- domain
- record ownership
- workflow state
- visibility scope
- sensitivity level
- launch vs hidden status

## 4.2. Permission Model

Recommended model:

- RBAC for broad role permission
- ABAC for record ownership, workflow state and visibility scope
- domain policy functions for sensitive actions

Example:

```txt
canEmployerSelectShiftWorker(user, shiftJob, application)
```

## 4.3. Role Context Rule

Every API request that affects role-specific data must know the active role context.

Allowed role contexts:

- employer
- employee
- hidden_admin_future

Rules:

- employer context cannot apply to jobs
- employee context cannot create employer jobs
- hidden admin context must not be exposed in public app
- role context changes must refresh navigation and permission state

## 4.4. Backend Permission Enforcement

Frontend hiding is not security.

Backend must enforce permission even if UI hides the button.

Rules:

- every create/update/delete action must be permission-checked
- every list/read endpoint must be ownership-filtered
- hidden domains must be server-blocked for public users
- audit-sensitive action must write audit event

## 4.5. Permission Denied Response

Safe response examples:

```txt
This action is not available in your current role.
This record is not available from this account.
This action is available only after the current step is complete.
```

Blocked:

- exposing private record existence
- exposing hidden Admin route details
- exposing internal security logic

# 5. API ARCHITECTURE

## 5.1. API Principle

API must be domain-safe and versioned.

Frontend must not directly control raw database tables.

Recommended direction:

```txt
Mobile/Web UI
→ API layer
→ service layer
→ domain policy layer
→ repository/data layer
→ database
```

## 5.2. API Versioning

Use versioned API routes.

Recommended:

```txt
/api/v1/auth
/api/v1/account
/api/v1/employer
/api/v1/employee
/api/v1/shift-jobs
/api/v1/career-jobs
/api/v1/work-vault
/api/v1/notifications
```

Rules:

- breaking changes require new API version or controlled migration
- mobile app version compatibility must be considered
- old app versions must fail safely

## 5.3. API Response Standard

Every API response should be predictable.

Success shape:

```json
{
  "success": true,
  "data": {},
  "meta": {}
}
```

Error shape:

```json
{
  "success": false,
  "error": {
    "code": "ACTION_NOT_ALLOWED",
    "message": "This action is not available in your current role."
  }
}
```

## 5.4. Error Code Families

Recommended error families:

- AUTH_REQUIRED
- INVALID_CREDENTIALS
- SESSION_EXPIRED
- ACTION_NOT_ALLOWED
- RECORD_NOT_FOUND
- VALIDATION_FAILED
- RATE_LIMITED
- ACCOUNT_DISABLED
- ACCOUNT_DELETION_PENDING
- SERVER_ERROR

## 5.5. Validation Rule

Validation must happen on:

- frontend for user guidance
- backend for actual security and data integrity
- database for final constraints where needed

Frontend validation alone is not enough.

## 5.6. Pagination and Search Rule

List endpoints must support:

- pagination
- safe filtering
- sorting
- role-safe search
- maximum page size

Avoid unbounded list APIs.

## 5.7. Idempotency Rule

High-impact actions should support idempotency where repeated requests may occur.

Examples:

- create application
- submit confirmation
- accept offer
- request account deletion
- revoke Work Vault access

# 6. DATABASE AND STORAGE ARCHITECTURE

## 6.1. Database Principle

Database must protect product truth.

Every important table/entity should include:

- stable ID
- owner/user reference
- role/domain reference
- status
- timestamps
- soft-delete/archive where needed
- audit link where needed

## 6.2. Recommended Database Type

Recommended production database:

- PostgreSQL or equivalent relational database for core workflow truth

Reason:

- strong relations
- transactions
- constraints
- audit-friendly
- scalable enough for Job Mitra
- good fit for role and ownership rules

## 6.3. Object Storage Rule

Uploaded files/documents must not be stored directly in normal database rows.

Use object storage for files.

Database stores:

- file metadata
- owner
- access scope
- storage key
- document status
- timestamps

Rules:

- private documents must be access-controlled
- signed URLs must be short-lived
- employer access must be scoped
- revoked access must stop future file access

## 6.4. Core Database Domains

Backend database should include:

1. accounts
2. employer profiles
3. employee profiles
4. role context records
5. Shift Jobs records
6. Career Jobs records
7. job draft records / draft metadata
8. Work Vault metadata
9. access grants
10. ratings/trust snapshots
11. notifications
12. audit logs
13. account deletion records
14. system settings / feature flags

## 6.5. Transaction Rule

Use database transactions for actions that update multiple related records.

Examples:

- select worker + create timeline event
- accept offer + update application state
- revoke vault access + create access history
- account deletion request + session revocation
- rating submission + trust snapshot update

## 6.6. Soft Delete / Archive Rule

Do not casually hard-delete workflow records.

Use:

- soft delete
- archive
- cancelled state
- revoked state
- deleted_at timestamp

Hard delete may be used only when safe and policy-compliant.

## 6.7. Migration Rule

Every schema change must have:

- migration file
- rollback plan where possible
- data compatibility review
- release note
- test result

No silent destructive migration.

## 6.13. Draft / Preview / Publish Backend Support

Backend must support safe employer job drafting before public publishing.

This applies to:

- Shift Jobs
- Career Jobs
- future employer-created public records where approved

### 6.13.1. Draft Status Model

Backend job records must support status values such as:

- draft
- draft_incomplete
- draft_ready
- preview_ready
- publish_confirmation_pending
- published
- closed
- archived

Rules:

- draft records are owner-only
- draft records must not appear in public employee discovery
- draft records must not accept applications
- draft records must not trigger employee notifications
- draft records must not affect trust/rating
- publish must be a deliberate state transition

### 6.13.2. Draft Ownership and Permission Rule

Only the owning employer account/role context may:

- create draft
- read draft
- update draft
- delete draft
- preview draft
- publish draft

Backend must block:

- employee access to employer draft
- other employer access to draft
- wrong-role draft publish
- hidden/future-domain draft publish in launch

### 6.13.3. Auto-save Support

Backend may later support server-side draft auto-save.

Rules:

- auto-save must never publish
- auto-save must preserve last saved state
- auto-save must be scoped to owner account
- server-side auto-save must not overwrite newer user edits incorrectly
- conflict handling is required for multi-device future support

Phase 0 may use local/device auto-save only.

### 6.13.4. Preview Before Publish Support

Preview endpoint/view should return employee-facing public-safe data only.

Preview must exclude:

- employer private notes
- internal/admin fields
- hidden-domain fields
- draft metadata not meant for employees
- security/audit internals

### 6.13.5. Duplicate Job Warning Support

Backend may provide duplicate warning checks before publish.

Duplicate warning may compare:

- employer ID
- job title
- category/work type
- date/time where relevant
- location/work area
- active/published status

Rules:

- duplicate warning is advisory only
- backend must not auto-merge jobs
- backend must not auto-delete jobs
- employer may continue if intentional

### 6.13.6. Publish Confirmation Support

Backend publish action must validate:

- required fields
- owner permission
- role context
- job domain
- current status
- public visibility rules
- Play Store/Phase-0 safe wording where relevant

Publish must create an audit/timeline event.

### 6.13.7. Draft Data Model

Recommended shared fields:

- draft_id_optional
- owner_employer_id
- source_domain
- draft_status
- completion_percent_optional
- last_saved_at
- last_previewed_at_optional
- duplicate_warning_shown
- publish_confirmed_at_optional
- created_at
- updated_at

Rule:

Draft support is a product-safety feature, not a hidden backend-only behavior.

# 7. LOCAL-FIRST TO BACKEND MIGRATION

## 7.1. Migration Principle

Current local-first behavior must not be destroyed when backend is introduced.

Backend must replace storage layers cleanly, not rewrite product logic randomly.

## 7.2. Migration Direction

Preferred direction:

```txt
Current UI
→ existing workflow services
→ backend-ready service interface
→ local adapter now
→ backend adapter later
```

## 7.3. Local Data Handling

When backend login launches, decide how to treat existing local data.

Options:

1. Reset local demo data after clear user notice
2. Import selected local data to account after user confirmation
3. Keep local demo mode separate from logged-in production mode

Recommended:

```txt
Keep local demo data separate from logged-in production data.
```

Reason:

- avoids accidental fake data upload
- avoids wrong account ownership
- safer for Play Store users
- cleaner production trust

## 7.4. Migration Warning

Do not silently upload old local/demo records into production account.

User must understand what is happening.

## 7.5. Offline / Weak Network Rule

Future backend app should handle:

- loading state
- retry state
- failed save state
- offline-safe draft where appropriate
- clear sync status

Do not fake saved state if server save failed.

# 8. SECURITY MASTER RULES

## 8.1. Security Baseline

Security must follow modern app and web security standards.

Minimum reference standards:

- OWASP ASVS v5.0 or latest stable version for web/backend security
- OWASP MASVS for mobile app security
- NIST SP 800-63 for digital identity guidance
- Google Play User Data and account deletion requirements

## 8.2. Transport Security

Required:

- HTTPS only
- no production API over plain HTTP
- secure cookies/tokens where used
- no tokens in URL
- certificate handling appropriate for mobile app

## 8.3. Secret Management

Blocked:

- secrets in frontend code
- secrets in GitHub public repo
- secrets in screenshots
- secrets in logs
- API keys embedded without restriction

Required:

- server-side environment variables
- secret rotation plan
- separate dev/staging/production secrets

## 8.4. Rate Limiting

Rate limiting required for:

- login
- signup
- OTP request
- password reset
- email verification
- account deletion request
- high-frequency search
- sensitive update actions

## 8.5. Input Security

Backend must protect against:

- injection
- invalid payloads
- mass assignment
- IDOR
- unsafe file uploads
- path traversal
- broken access control
- excessive data exposure

## 8.6. Logging Security

Logs must not contain:

- passwords
- OTPs
- tokens
- private documents
- full sensitive identity values
- hidden security scoring details

Logs should contain:

- request ID
- actor ID where safe
- action
- result
- timestamp
- error code
- domain

## 8.7. Audit Log Rule

Audit logs required for:

- login/security events
- role change
- job publish
- applicant selection
- Work Vault access grant/revoke
- rating edit
- trust correction
- account deletion request
- admin/future governance action

Audit logs must not be editable through normal app flows.

- account data
- profile data
- job/application data
- Work Vault metadata/documents
- ratings/trust data
- notifications
- logs

- verified identity
