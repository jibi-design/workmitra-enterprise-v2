# 09. Product UI Standard

## 1. Final Decision

### 1.1 Master UI Standard

This document defines the common UI standard for Mitra Labs products, websites, domains, and future product interfaces.

### 1.2 Scope

This document covers:

```txt
Job Mitra
Career Jobs
Shift Jobs
Workforce Ops
HR / Manager / Admin UI boundaries
HomeFix Mitra
Mitra Labs website
Future products
```

### 1.3 Core Rule

Every product and domain must have a clear visual identity, but the full Mitra Labs ecosystem must still feel consistent, premium, readable, and role-safe.

## 2. Global UI Standard

### 2.1 Global Quality Rule

All pages must be:

```txt
clean
premium
high-readable
mobile-first
role-safe
simple to understand
not visually overloaded
```

### 2.2 Global Design Rule

Use:

```txt
clear headings
short helper text
strong contrast
rounded premium cards
soft shadows
compact spacing
clear section hierarchy
clear empty states
```

Avoid:

```txt
crowded layouts
too many repeated cards
weak contrast
unclear buttons
mixed domain colors
fake feature claims
unnecessary long pages
```

### 2.3 Global User Understanding Rule

A normal user must understand:

```txt
where they are
what this page does
what action is primary
what data is empty
what will appear later
what is clickable
what is only explanation
```

## 3. Product Hierarchy Rule

### 3.1 Job Mitra Role Hierarchy

Always maintain:

```txt
Shift Jobs < Employee Career Jobs < Employer Career Jobs
```

Meaning:

```txt
Shift Jobs = fast, clear, operational
Employee Career Jobs = premium, calm, career-focused
Employer Career Jobs = higher-authority, command-center, decision-maker level
```

### 3.2 HomeFix Mitra Role Hierarchy

HomeFix Mitra must keep different role experiences separated:

```txt
Customer / Home Owner
Independent Technician
Shop Technician
Shop Owner
```

Each role must have clear UI, but must not mix responsibility or data ownership.

### 3.3 Admin Hierarchy

Admin UI must feel more controlled and system-level than public apps.

Admin UI must not look like a public user app page.

## 4. Domain Color Rules

### 4.1 Global Color Rule

Each domain can have its own color identity.

Never mix colors randomly across domains.

### 4.2 Career Jobs Color Rule

Career Jobs must use only Career blue family colors.

Allowed:

```txt
Career blue
Deep blue
Soft blue
Blue-tinted white/gray
Neutral slate/gray text
White card surfaces
```

Avoid:

```txt
orange
green
Shift Jobs colors
HR colors
Admin colors
mixed domain colors
```

Red is allowed only for real error/destructive states.

### 4.3 Shift Jobs Color Rule

Shift Jobs should keep its own separate domain color identity.

Do not reuse Career blue in a way that makes Shift Jobs look like Career Jobs.

Shift Jobs should feel:

```txt
fast
temporary
operational
shift-focused
clear
less executive than Career Employer pages
```

### 4.4 Workforce Ops Color Rule

Workforce Ops must have its own domain identity.

It must not visually merge with Career Jobs or Shift Jobs.

### 4.5 HomeFix Mitra Color Rule

HomeFix Mitra should keep a premium service/home-care feel.

Do not copy Job Mitra Career UI colors directly if it causes product confusion.

### 4.6 Admin Color Rule

Admin UI should use controlled system colors.

Admin UI should avoid playful/public app styling.

## 5. Count and KPI Rule

### 5.1 Zero Count Rule

If count is 0:

```txt
soft gray
low emphasis
not visually dominant
```

### 5.2 Active Count Rule

If count is 1+:

```txt
domain color
stronger emphasis
clear active state
```

### 5.3 KPI Repetition Rule

Do not repeat the same KPI information in multiple sections unless it has a different purpose.

If hero already shows a summary, avoid repeating the same zero boxes below.

### 5.4 KPI Clarity Rule

Counts must clearly say what they mean.

Example:

```txt
0 active
0 applications
0 workspace records
```

Bad:

```txt
0
0
0
```

without clear labels.

## 6. Empty State Rule

### 6.1 Empty State Purpose

Empty states must explain:

```txt
what is missing
why it is empty
what will appear later
what the user can do next
```

### 6.2 Empty State Safety

Empty states must not pretend data exists.

Do not create fake backend claims.

Do not show fake activity.

### 6.3 Empty State Click Rule

If an empty state is only a guide, it must not be clickable.

If it is clickable, the action must be clear.

Example:

```txt
Create Career Job button = create post
Empty pipeline card = guide only
Hired Employee Workspaces card = workspace area
```

## 7. Button and Action Rule

### 7.1 Primary Action Rule

Each page should have one clear primary action.

### 7.2 Secondary Action Rule

Secondary actions should be softer and less dominant.

### 7.3 Paired Button Rule

If two buttons are placed together, they must feel visually balanced.

Avoid one strong button and one weak/unpolished button unless hierarchy is intentional.

### 7.4 Click Meaning Rule

Every clickable card/button must clearly open the correct flow.

Do not make a guide card open an unrelated create page.

## 8. Job Mitra UI Standard

### 8.1 Job Mitra Common Rule

Job Mitra UI must clearly separate:

```txt
Employee
Employer
Admin
Career Jobs
Shift Jobs
Workforce Ops
Future HR/Manager areas
```

### 8.2 Job Mitra Public App Rule

Public app UI must not expose admin controls.

### 8.3 Job Mitra Domain Rule

Career Jobs, Shift Jobs, Workforce Ops, HR, Manager Console, and Admin must not visually or functionally mix.

## 9. Career Jobs UI Standard

### 9.1 Career Jobs Reference Pages

Completed reference pages:

```txt
Employee Career Jobs Home
Employer Career Jobs Home
```

These are the reference standard for remaining Career Jobs pages.

### 9.2 Employee Career Page Rule

Employee Career pages should feel:

```txt
premium
calm
career-focused
simple
clear
not employer-authority level
```

### 9.3 Employer Career Page Rule

Employer Career pages should feel:

```txt
Premium Hiring Command Center
high-authority
decision-maker focused
more executive than employee pages
clear create/hiring/workspace flow
```

### 9.4 Career Workspace Rule

Hired Employee Workspaces should be visible and understandable.

Workspace means:

```txt
Career Job hire record
joined / working / notice / resignation / completion / rating follow-up
```

Workspace is not:

```txt
HR
Payroll
Shift Job group
Admin
Manager Console
```

### 9.5 Career Flow Rule

Correct Career flow:

```txt
create post -> receive applicants -> shortlist/offer -> hire -> workspace appears
```

## 10. Shift Jobs UI Standard

### 10.1 Shift Jobs Meaning

Shift Jobs are for temporary, urgent, short-term, daily, weekly, or monthly work.

### 10.2 Shift Jobs UI Feel

Shift Jobs should feel:

```txt
fast
practical
worker-ready
shift-focused
less formal than Career Jobs
clear status-driven
```

### 10.3 Shift Jobs Separation Rule

Shift Jobs must stay separate from Career Jobs.

Never mix:

```txt
Shift groups with Career workspaces
Shift worker flow with Career employee lifecycle
Temporary work with permanent employment records
```

### 10.4 Shift Jobs Visibility Rule

Shift Jobs pages should prioritize:

```txt
shift requirement
worker availability
selection/waiting list
group/workspace
status
communication boundary
```

## 11. Workforce Ops UI Standard

### 11.1 Workforce Ops Meaning

Workforce Ops is an operations/workforce management domain.

### 11.2 Workforce Ops Boundary

Workforce Ops must not become Career Jobs, Shift Jobs, or HR Management.

### 11.3 Workforce Ops UI Feel

Workforce Ops should feel:

```txt
structured
operational
team/workforce focused
less hiring-focused than Career Jobs
less temporary than Shift Jobs
```

## 12. HR / Manager / Admin UI Boundary

### 12.1 HR Boundary

HR Management is a future/advanced domain.

Do not mix HR with Career workspace.

Career workspace only handles Career Job employment lifecycle status, not full HR.

### 12.2 Manager Console Boundary

Manager Console is separate from normal Employer Career Home.

Do not expose Manager Console in public app unless approved.

### 12.3 Admin Boundary

Admin must stay inside:

```txt
admin.mitralabs.app
```

Admin must not be inside public Job Mitra or HomeFix Mitra apps.

## 13. HomeFix Mitra UI Standard

### 13.1 HomeFix Mitra Role Separation

HomeFix Mitra must clearly separate:

```txt
Customer / Home Owner
Independent Technician
Shop Technician
Shop Owner
```

### 13.2 HomeFix Mitra UI Feel

HomeFix Mitra should feel:

```txt
trustworthy
service-focused
home-care focused
premium but simple
high-readable
universal/global-friendly
```

### 13.3 HomeFix Mitra Safety Rule

Do not overclaim features.

If a feature is local-only, UI wording must not present it as cloud/verified/real backend behavior.

### 13.4 HomeFix Mitra Data Flow Rule

Service, bill, complaint, property, appliance, and provider flows must stay linked correctly.

## 14. Admin UI Standard

### 14.1 Admin UI Feel

Admin UI should feel:

```txt
secure
controlled
system-level
professional
audit-focused
permission-aware
```

### 14.2 Admin UI Must Show

Admin pages must clearly show:

```txt
product context
role/permission context
dangerous actions
audit-sensitive actions
filters/search
status
logs where needed
```

### 14.3 Admin UI Must Avoid

Admin UI must avoid:

```txt
public app style
decorative confusion
unclear destructive buttons
hidden permission assumptions
mixing product data
```

## 15. Play Store and Trust UI Rule

### 15.1 No Fake Claims

Do not show fake:

```txt
OTP
payment
notification
verification
AI ranking
interview scheduled
offer confirmation
real-time messaging
```

unless real backend data exists.

### 15.2 Local/Demo Rule

If a feature is local/demo-only, wording must be honest.

### 15.3 Trust Rule

Users must never feel the app promised a real backend/cloud workflow when it is not actually implemented.

## 16. Page Review Rule

### 16.1 Review Checklist

Every page must be checked for:

```txt
role separation
domain color correctness
primary action clarity
empty state clarity
KPI/count meaning
readability
mobile spacing
no fake claims
no repeated confusing information
correct clickable behavior
```

### 16.2 Approval Rule

A page should not be final-locked unless it reaches the expected product/domain standard.

### 16.3 Career Page Rating Target

Career pages should target:

```txt
Employee Career pages: 9.0+
Employer Career pages: 9.5+
```

## 17. Approval Status

### 17.1 Current Status

```txt
Draft
```

### 17.2 Review Flow

```txt
Draft -> Reviewed -> Approved -> Locked
```

### 17.3 Lock Rule

This product UI standard must be approved before using it as the final UI reference for future Job Mitra, HomeFix Mitra, admin, or Mitra Labs pages.
